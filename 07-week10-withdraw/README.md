## 1. Суть задания и архитектура

На 10 неделе в смарт-контракт Liquidity Vault добавляется возможность вывода средств пользователем (`withdraw`).
Пользователь возвращает свои share-токены («квитанции»), контракт их сжигает и взамен возвращает базовые токены из хранилища пропорционально доле.

### Формула расчёта вывода:
```text
tokens_out = shares_amount * total_tokens / total_shares
```
Все вычисления выполняются в целочисленной арифметике с приведением к `u128` для защиты от переполнения и проверкой деления на ноль.

## 2. Механизм Cross-Program Invocation (CPI)

Инструкция `withdraw` выполняет два последовательных вызова системной программы SPL Token Program:

1. **Сжигание share-токенов (`token::burn`):**
   - Токены сжигаются с аккаунта `user_share_account`.
   - Подписывает транзакцию сам пользователь (`authority: user`), так как он владеет сжигаемыми долями.

2. **Перевод токенов из хранилища (`token::transfer`):**
   - Базовые токены переводятся из `vault_token_account` на `user_token_account`.
   - Владельцем аккаунта `vault_token_account` является PDA хранилища `vault_state`. У PDA нет приватного ключа, поэтому вызов подписывает сам контракт от имени PDA через `CpiContext::new_with_signer` с использованием сидов:
     `&[b"vault", token_mint_key.as_ref(), &[vault_state.bump]]`.

3. **Обновление состояния:**
   - `vault_state.total_tokens -= tokens_out`
   - `vault_state.total_shares -= shares_amount`
   - `user_card.deposited = card.deposited.saturating_sub(tokens_out)`
   - `user_card.shares = card.shares.saturating_sub(shares_amount)`

## 4. Вопросы для самопроверки из методички

- **Что такое CPI и зачем он нужен?**
  CPI (Cross-Program Invocation) - механизм вызова одной программы Solana из другой во время выполнения одной транзакции. Программе vault не требуется заново реализовывать логику токенов, балансов и проверок подписей: она напрямую вызывает системную SPL Token Program, что обеспечивает надежность и стандартизацию.

- **Когда подписывает пользователь, а когда программа?**
  Пользователь подписывает операции со своими собственными активами (сжигание своих share-токенов). Программа подписывает операции с активами пула от имени PDA хранилища (`vault_state`), подтверждая свои права через программные сиды без использования приватного ключа.

- **Почему администратор не может просто забрать токены из vault своей подписью?**
  Аккаунт с токенами пула (`vault_token_account`) принадлежит не администратору, а адресу программы (PDA). Распоряжаться токенами хранилища может только логика инструкций контракта (`withdraw`, а в будущем `swap` и открытие позиций в пулах ликвидности). У администратора нет технической возможности подписать перевод в свой карман в обход правил смарт-контракта.

## 5. Тестирование контракта (tests/vault.ts)

Тестовый набор покрывает полный жизненный цикл и граничные случаи:
1. `initialize_vault`: создание хранилища, аккаунта токенов и share mint.
2. `create_user_card`: создание карточек для пользователей A и B.
3. Запрет повторного создания карточки для одного пользователя.
4. Депозит A (100 токенов -> 100 shares).
5. Депозит B (50 токенов -> 50 shares).
6. Запрет депозита без карточки пользователя.
7. Запрет нулевого депозита.
8. Вывод A: возврат 50 shares -> получение 50 токенов.
9. Вывод B: полный вывод 50 shares -> сожжение всех долей и возврат 50 токенов.
10. Запрет вывода с суммой 0.
11. Запрет вывода больше имеющихся shares.
12. Запрет вывода без карточки.
